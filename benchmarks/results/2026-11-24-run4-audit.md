# Manual applicability audit: run 4, top 10 findings per target

**This is manual judgement**, not a measurement. It covers each target's
top 10 findings by VulnSight rank, from `2026-11-24-run4.json`.

Every finding is "version-applicable": NVD lists the detected version as
affected. The audit asks a narrower question: does the vulnerable
component exist and run in *this* container's configuration?

| Label | Meaning |
|---|---|
| **A** (applicable) | The vulnerable code path is present and enabled. Exploitability may still depend on deployment details. |
| **N** (not applicable) | Needs a module, feature, platform or config this container doesn't have. |
| **U** (unclear) | Can't tell from the advisory and the container config. |

Config facts were checked inside the running containers on 2026-11-24:
- **httpd**: none of mod_lua, mod_sed, mod_proxy*, mod_rewrite or mod_cgi
  is loaded.
- **Tomcat 8.5.19 / 9.0.30**: the AJP connector is enabled on 8009.
  Default servlet is read-only. No CORS filter.
- **nginx**: compiled with http_v2 and mp4, but the config uses neither.
  No autoindex, resolver or TLS.
- **Jetty**: start.ini enables only `http` (no http2, ssl, gzip or jaspi).
- **Elasticsearch 1.1.1 / 1.4.2**: `groovy-all-2.3.2.jar` is bundled in
  both.
- **MySQL**: SSL status could not be checked (root password unknown), so
  yaSSL CVEs are U.

Most top-ranked version-applicable CVEs (48 of 80) are **not applicable**
to these default configurations. They need an optional module (HTTP/2,
mod_proxy, mod_lua), TLS, or an auth scheme the target doesn't use.
Version-only CVE matching can't see this. It is the main source of noise
in VulnSight's (and any version-based scanner's) findings.
